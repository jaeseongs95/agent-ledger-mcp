# veridger 6.0.0

## English

### Summary

`6.0.0` adds an administration console that navigates without full page reloads, a workspace for project versions, and automatic PostgreSQL schema migration on configured hosts. This is a major release because existing MCP detail responses have a new field.

### Breaking changes

- `ledger_spec`, `ledger_task` and `ledger_criterion` now return `project_versions`, an array of linked version names. The same field appears in the corresponding details from `ledger_get` when `include_details=true`. Clients that enforce the previous response schema must accept the new field.
- Both services require `Schema-Version: V16`. Apply the new database migration before starting them.

### Migration

1. Download the `6.0.0` release assets and verify them against `SHA256SUMS`. Stop both services and back up the database, installed JARs, configuration and `.installed-version`. Verify that the database backup can be restored.
2. Run the new installer with the existing database and installation settings. Use `sudo sh install.sh --version=v6.0.0` on Linux or `install.cmd --download v6.0.0` from an administrator terminal on Windows. The installer applies `V16__project_version_items.sql` and preserves existing issue-to-version links.
3. To enable automatic PostgreSQL schema upgrades for future releases, pass `--pg-dump=<absolute-path>` to the Linux installer or set `VERIDGER_PG_DUMP` to the full path of `pg_dump.exe` before running the Windows installer. Provide the database owner credentials through the installer prompt or its standard input.
4. Confirm that both services report `UP` at `/healthz` and that existing version links are visible in the project version workspace.
5. To return to `5.0.0`, stop both services and restore the matching database backup, JARs, updater, configuration and installed version marker. Then start the services and check `/healthz` again. A database restore discards changes made after the backup.

### New

- The project version workspace lets administrators create and link issues, specifications, tasks and release criteria and navigate between versions and linked records.
- An agent can associate a new record with a registered version by providing `project_version` on a `save` operation in `ledger_batch`. Record creation and version linking share a transaction and use the existing project permissions.
- The host updater checks the candidate's migration history, backs up the PostgreSQL database and applies pending migrations before restarting the services when automatic schema updates have been configured.

### Changed

Admin navigation preserves browser history and supports direct links. Filters and table layouts use the available space across narrow and wide screens.

### Removed

No MCP tools or deployment settings were removed.

### Security

Automatic migration uses database owner credentials accessible only to the privileged host updater. The updater verifies the release JARs before using them.

### Requirements

- `JDK 25` for server and client hook runtimes.
- Database on `Schema-Version: V16`.
- Automatic schema upgrades require PostgreSQL, an executable `pg_dump` and the database owner credentials provisioned at installation.

### Known limitations

- The `5.0.0` `/updates` page cannot apply this schema change. Use the installer for this upgrade.
- If an update fails after database migration begins, restore the database and matching installation from backup before restarting the previous version.

## 한국어

### 요약

`6.0.0`은 페이지 전체를 새로고침하지 않는 관리 콘솔, 프로젝트 버전 작업 공간, 설정된 호스트에서 PostgreSQL 스키마를 자동으로 이전하는 기능을 추가합니다. 기존 MCP 상세 응답에 필드가 추가되어 주 버전을 올렸습니다.

### 호환되지 않는 변경

- `ledger_spec`, `ledger_task`, `ledger_criterion`은 연결된 버전명 배열인 `project_versions`를 반환합니다. `ledger_get`에서 `include_details=true`를 지정할 때도 해당 유형의 상세 결과에 이 필드가 추가됩니다. 이전 응답 스키마를 엄격히 검증하는 클라이언트는 새 필드를 허용해야 합니다.
- 두 서비스에 `Schema-Version: V16`이 필요합니다. 서비스를 시작하기 전에 새 데이터베이스 마이그레이션을 적용합니다.

### 이전 절차

1. `6.0.0` 릴리스 파일을 내려받아 `SHA256SUMS`로 검증합니다. 두 서비스를 중지하고 데이터베이스, 설치된 JAR, 설정과 `.installed-version`을 백업합니다. 데이터베이스 백업을 복원할 수 있는지 확인합니다.
2. 기존 데이터베이스 및 설치 설정으로 새 설치기를 실행합니다. Linux에서는 `sudo sh install.sh --version=v6.0.0`을 사용하고 Windows에서는 관리자 터미널에서 `install.cmd --download v6.0.0`을 실행합니다. 설치기는 `V16__project_version_items.sql`을 적용하고 기존 이슈와 버전의 연결을 보존합니다.
3. 이후 릴리스부터 PostgreSQL 스키마를 자동으로 갱신하려면 Linux 설치기에 `--pg-dump=<absolute-path>`를 전달하거나 Windows 설치기를 실행하기 전에 `VERIDGER_PG_DUMP`에 `pg_dump.exe`의 전체 경로를 설정합니다. 설치기의 입력 안내 또는 표준 입력으로 데이터베이스 소유자 자격 증명을 전달합니다.
4. 두 서비스의 `/healthz`가 `UP`인지, 프로젝트 버전 작업 공간에서 기존 버전 연결을 볼 수 있는지 확인합니다.
5. `5.0.0`으로 되돌리려면 두 서비스를 중지하고 해당 버전의 데이터베이스 백업, JAR, 업데이터, 설정과 설치 버전 표시를 복원합니다. 서비스를 시작한 뒤 `/healthz`를 다시 확인합니다. 데이터베이스를 복원하면 백업 이후에 반영된 변경 사항은 사라집니다.

### 추가

- 관리자는 프로젝트 버전 작업 공간에서 이슈·명세·작업·출시 기준을 생성하고 연결할 수 있으며, 버전과 연결 항목 화면을 오갈 수 있습니다.
- 에이전트는 `ledger_batch`의 `save` 작업에 `project_version`을 지정해 새 항목을 등록된 버전에 연결할 수 있습니다. 항목 생성과 버전 연결은 한 트랜잭션으로 수행하고 기존 프로젝트 권한을 적용합니다.
- 스키마 자동 갱신을 설정한 호스트의 업데이터는 후보 버전의 마이그레이션 이력을 검사하고 PostgreSQL 데이터베이스를 백업한 뒤, 서비스를 다시 시작하기 전에 미적용 마이그레이션을 실행합니다.

### 변경

관리 콘솔의 화면 이동은 브라우저 이력을 유지하고 화면별 직접 링크를 지원합니다. 필터와 표는 좁고 넓은 화면의 가용 공간에 맞춰 배치합니다.

### 제거

제거된 MCP 도구나 배포 설정은 없습니다.

### 보안

자동 마이그레이션에 사용하는 데이터베이스 소유자 자격 증명은 권한이 부여된 호스트 업데이터만 읽을 수 있습니다. 업데이터는 사용 전에 릴리스 JAR를 검증합니다.

### 요구 사항

- 서버와 클라이언트 훅 실행에 `JDK 25`가 필요합니다.
- 데이터베이스에 `Schema-Version: V16`이 필요합니다.
- 자동 스키마 갱신에는 PostgreSQL, 실행 가능한 `pg_dump`, 설치 시 등록한 데이터베이스 소유자 자격 증명이 필요합니다.

### 알려진 제한

- `5.0.0`의 `/updates` 화면에서 이번 스키마 변경을 적용할 수 없습니다. 이번 업그레이드에는 설치기를 사용합니다.
- 데이터베이스 마이그레이션이 시작된 후 업데이트가 실패하면 이전 버전을 시작하기 전에 데이터베이스와 해당 설치 환경을 백업에서 복원합니다.
