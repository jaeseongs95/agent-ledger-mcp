# pg-ledger-mcp 2.0.0

## English

### Summary

2.0.0 replaces the 1.x implementation (DBHub, Node, PostgreSQL functions and triggers, raw SQL tools) with a universal domain-neutral ledger written in Java 25 and Spring Boot 4.1. It serves software, film production, writing, research and operations with issues, specifications, tasks, milestone criteria, deliverables and independent reviewer verification. Every MCP response uses the `ApiResult.v1` envelope (`schemaVersion` `"1.0.0"`, `ok`, `data`, `error`), every write tool takes flat validated arguments and a required `operationKey`, and callers can authenticate either with standard per-author HTTP `Bearer` session tokens (`lgt_...` in `STANDARD` `ledger.mcp.auth-mode`, issued by `token-issue`) or with Ed25519 `_hostAttestation` tokens. The SQL is ANSI and no DBMS-specific feature is used: a JDBC driver is attached by the user and is not bundled, and the row limit of a list, the declaration of the long text column type and the probe that proves the encoding of the database, the three places that differ by product, are chosen by `SqlBuilder`. PostgreSQL is the tested database of this edition; other products may work but are not tested and receive no product-specific tailoring outside these three places. Timestamps are stored and transmitted in UTC. Version 2.0 itself contains no handling of 1.x: its services, its installers and `ledger-cli` read no 1.x setting, file or table. An existing 1.x installation is moved by a separate tool, `ledger-migrate-1x.jar`, with the four commands `stop-1x`, `import-secrets-1x`, `import-1x` and `retire-1x`.

### Breaking changes

1. **Result wrapping replaced by `ApiResult.v1`.** DBHub wrapped each write result as `rows[0].result`. Every tool now returns `ApiResult.v1` (`schemaVersion`, `ok`, `data`, `error`) with payload keys (`status`, `entity`, `id`, `version`, `history_id`, and so on) inside `data`. A client that reads `rows[0].result` must read from `data`.
2. **Raw SQL tools removed.** `execute_sql_reader` and `search_objects_reader` no longer exist. The fifteen structured read tools `ledger_get`, `ledger_issue`, `ledger_spec`, `ledger_task`, `ledger_criterion`, `ledger_history`, `ledger_search`, `ledger_issues`, `ledger_specs`, `ledger_tasks`, `ledger_criteria`, `ledger_attention`, `ledger_stats`, `ledger_projects` and `ledger_codes` replace them. Queries that read the schema directly have no equivalent.
3. **Caller authentication and `_hostAttestation` changed.** In `STANDARD` `ledger.mcp.auth-mode` (default), callers may authenticate with a per-author `Bearer` session token (`lgt_...`) without `_hostAttestation`. When `_hostAttestation` is used, a bare `<vendor>:<session-id>` is refused with `ATTESTATION_UNSIGNED`. The new value is `pgla2.<author>.<tool>.<operation key>.<arguments digest>.<issued at>.<signature>`: an Ed25519 signature that also covers the SHA-256 of the RFC 8785 canonical form of the arguments. The operation key is the `operationKey` argument of the call. Only the new hook jar produces it.
4. **Existing grants need a session key or session token.** `import-1x` copies the old grants without a key, so a write of an imported author is refused with `ATTESTATION_SIGNATURE_INVALID` until the owner registers a session key with `key-register` (or issues a session token with `token-issue`). The grant then works as before.
5. **1.x request receipts are not carried over.** `import-1x` copies no receipt. Every write of 2.0 needs an `operationKey` and the old `request_id` is refused as an unknown argument, so a 1.x client that retries with `request_id` is refused and writes nothing: a 1.x answer that was lost cannot cause a second write in 2.0. The `request_id` of a 1.x history row is kept as its `operation_key`. `REQUEST_ID_LEGACY` is removed: an operation key is refused only as a duplicate under the normal rules (`OPERATION_CONFLICT`).
6. **Settings moved.** The 1.x environment file is gone. Secrets are stored with `secret-set`, and the deploy settings are the Spring Boot properties listed in the README. The token of the agents of the 1.x environment file is moved into the secret store by `import-secrets-1x`; the admin token is not (the installer makes the one of 2.0 with `token-generate`).
7. **The admin web signs in with the admin token, OpenID Connect or a passkey, and every change is approved by a passkey.** The admin token signs a browser in only with `ledger.admin.sign-in=token` (the personal edition; it also stays the bearer of the read-only JSON endpoints); with `oidc` or `passkey` the login page has no token form. Choose the sign-in with `ledger.admin.sign-in` (exactly one of `token`, `oidc` or `passkey`; the default is `passkey`; an installation with `ledger.admin.oidc.*` settings and no choice is refused at start). The OpenID Connect owner is one e-mail address, `ledger.admin.oidc.owner-email`, at the issuer `ledger.admin.oidc.issuer`. Register the first passkey with the one-time code of `ledger-cli passkey-code`.
8. **The input of the write tools is flat and validated; no old form is accepted.** Dedicated flat tools (`ledger_issue_save`, `ledger_spec_save`, `ledger_task_save`, `ledger_criterion_save`, `ledger_transition`, `ledger_record_deliverable`, `ledger_record_case`, `ledger_link`, `ledger_correct`, `ledger_review`, `ledger_review_correct` and `ledger_batch`) replace polymorphic maps and take a required `operationKey` (1 to 128 characters, for example a UUID) that replaces `request_id` and `batch_request_id`: the same key with the same arguments returns the stored answer and writes once, the same key of the same author with other arguments is `OPERATION_CONFLICT` (the keys belong to the author, like those of `artifact_begin`: another author may use the same key), and a missing or empty key is `VALIDATION_FAILED` (path `operationKey`); the server never makes a key up, and the hook adds none. `ledger_batch` takes one key for the batch and its operations carry none; the batch is one request, so the same key with other operations or under another tool is `OPERATION_CONFLICT`. JSON `null` on an optional field counts as not given; an optional text field is cleared with an empty text. `artifact_chunk` and `artifact_finish` take no `operationKey` (an upload starts with the `operationKey` of `artifact_begin`; a chunk is idempotent by `uploadId`, `sequence` and `chunkSha256`, finish by `attachmentId`). The `author_id` argument is gone. An object or an array argument must be sent as that JSON value, not as a JSON document in a string, and the text `null` is a text, not a missing argument. An unknown argument, `request_id`, `batch_request_id` and `author_id` included, is refused. The `request_id` column of the history is `operation_key`, and the history output field is `operation_key`.

### Migration

1. Install the hook jar on every client host first, with a Java 25 runtime on the `PATH`. Writes without a signing hook are refused with `HOST_ATTESTATION_REQUIRED`.
2. Back up and stop the 1.x services. Back up the ledger database with the dump tool of your DBMS and copy `/etc/pg-ledger-mcp`
   (the 1.x file `/etc/pg-ledger-mcp/env` holds the 1.x secrets) and the 1.x unit files. Then run `stop-1x` as root on the host of 1.x. It stops and
   disables the services `<name>` and `<name>-admin` (default name `pg-ledger-mcp`) and keeps each definition as a backup: the unit file moves to
   `<unit>.1x-backup` (1.x had Linux installations with systemd units only, so `--platform=windows` is refused with `NO_1X_SERVICE_WINDOWS`). Java has no API for the
   service manager, so the command runs `systemctl` with fixed arguments, and it touches only a service of that name whose definition is the one of 1.x
   (`NOT_1X_SERVICE` otherwise, with nothing changed). The public host names of 1.x are not lost silently: with `--env=<file>` the command reads
   the host names that `DBHUB_ALLOWED_HOSTS` of 1.x (for 1.1.0 also `PGLEDGER_ADMIN_ALLOWED_HOSTS`) allows and, before it stops anything, tells the public names that the one
   `--mcp-host` (or `--admin-host`), the options that you will give the installer, does not carry, as names that 2.0 no longer accepts (the installer takes one host name for each
   service); it refuses nothing for them. Give the name as `--mcp-host=<name>`. It can be run again, and it prints how to return to 1.x.

```sh
sudo java -jar dist/ledger-migrate-1x.jar stop-1x --env=/etc/pg-ledger-mcp/env --mcp-host=<mcp-host> --admin-host=<admin-host>
```

3. Create the two database accounts with the tools of your DBMS, the application account and the DDL account, obtain the JDBC driver
   yourself, and install the 2.0.0 jars with the installer of the host; the installers know nothing of 1.x, and `--mcp-host` and `--admin-host` take the same host names
   as in step 2. The 1.x schema stays untouched and is only read. The installer
   stores the secrets (`secret-set`, `token-generate`), registers the driver, creates the schema with `migrate`, applies `dml-grants.sql`
   to the application account and starts the two services; a file that it did not render and that a rendered file replaces is kept as `<file>.backup`. The README (Installation) describes the three targets: a personal PC, a
   Windows server and a Linux server.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url>
```

```bat
deploy\install.cmd dist <winsw-exe> <driver-jar> <driver-class> <ddl-account> <app-account> "<jdbc-url>"
```

4. Move the secrets of 1.x with `import-secrets-1x`, after the installer: the secret store belongs to the service account, so root opens the 1.x file and gives it on
   standard input to the tool, which runs as the service user. The installer generated tokens of its own, so `--replace` replaces them by the 1.x values, which keeps the
   clients working (the admin token of 1.x is not imported: the admin web signs in with the one that the installer made); no value is printed, and without `--replace` a secret that exists is kept. Then restart the two services of 2.0.0 with
   `sudo systemctl restart pg-ledger-mcp pg-ledger-mcp-admin`.

```sh
sudo sh -c 'runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar import-secrets-1x --replace --stdin < /etc/pg-ledger-mcp/env'
```

| 1.x environment value | 2.0.0 secret |
|---|---|
| `DBHUB_AUTH_TOKEN` | `ledger.mcp.token`, and the same value as `ledger.admin.agent-token` |
| `PGLEDGER_ADMIN_TOKEN` | not imported: the `ledger.admin.token` that the installer made with `token-generate` is the admin token of 2.0 (a token chosen by hand may be weaker; the command says so when the 1.x environment has the setting) |
| database password of the ledger logins | `ledger.jdbc.password`, typed by the installer for the application account |

5. Import the 1.x ledger once with `import-1x`, on the schema that `migrate` and `setup` made (the state after the installer, which runs `setup`). The import reads the 1.x schema read only, copies everything in one transaction and compares the number of rows and the SHA-256 digest of every table; `--verify-only` repeats only the comparison. It accepts the seed codes and the audit rows that `setup` wrote (a seed code that 1.x also has takes the 1.x values), it refuses when a table of ledger data, a session key or an earlier import is already there, and it lists every value that the new schema cannot hold (an id with whitespace, two ids that differ only in case, a text longer than its column) without writing anything; correct those rows in the 1.x ledger and run it again. The ids of 1.x are kept as they are: an id of a task or a condition is 1 to 120 characters without whitespace or control characters, in any case and with any characters (`:`, `/`, `#`, `.`, `_`, `-` ...), and defect ids keep their form (`<CODE>-D-0001`). Ids of one kind that differ only in case are one id to the new schema (a lookup compares the id exactly, and the key of the id in upper case is unique on every DBMS), so the import refuses such a pair and a task or condition cannot be created with an id that equals an existing one when the case is ignored (`DUPLICATE_KEY`). An empty text of 1.x (`purpose`, `success_condition`, `behavior`, `root_cause` and `condition_text` allowed `''`) is stored as NULL and the tools return an empty string for it, as 1.x did. The `code` of a condition (200 characters) and the `ci_ref` (2000 characters) are longer than in the earlier 2.0 builds, and the `origin_ref` of a task is a long text (up to 20000 characters when written), so every value of 1.x fits. No tool schema carries a pattern for an id.

The request receipts of 1.x are not copied (see Breaking changes). The settings `ledger.import.source.url`, `ledger.import.source.username`, `ledger.import.source.schema` and the secret `ledger.import.source.password` belong to the tool; run the commands as the service user.

```sh
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-cli.jar secret-set ledger.import.source.password
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar import-1x --owner-account=<ddl-account> --ledger.import.source.url=<jdbc-url> --ledger.import.source.username=<account>
```

6. Every author registers a session key. The session prints its public key and fingerprint, and the owner compares the fingerprint and registers the key on the server it was made for; the grants of that author then work.

```sh
java -jar ledger-client-hook.jar session-key <server> <author>
java -jar ledger-cli.jar key-register <author> <public-key-or-block> <fingerprint>
```

7. Switch the clients: replace the calls of `execute_sql_reader` and `search_objects_reader` by the read tools, and read the keys of a write result from the result itself. Check the server with `mcp-check` and `import-1x --verify-only`.
8. To go back, stop the 2.0.0 services, put each `<unit>.1x-backup` back under its own name (copy it, so that the backup stays), run `sudo systemctl daemon-reload`, and run `sudo systemctl enable --now <name>` and the same for `<name>-admin` to start the 1.x services with their previous configuration. `stop-1x` prints these steps. The import never changes the 1.x schema.
9. When you accept 2.0, remove what the 1.x installer made in the database. The kept units and the 1.x schema are the way back until then, and nothing deletes them before. Make a `pg_dump` backup of the 1.x database and test its restore, stop the 1.x service, and run `retire-1x` with an account that owns the 1.x objects (`ledger.import.source.username`). Without options it checks that the ledger of 2.0 still holds what 1.x held (rows that 2.0 added or edited since are accepted; `import-1x --verify-only` is stricter and reports them as differences) and that no other session uses the 1.x schema, prints every object in the order it is dropped and the SHA-256 of that list, and changes nothing. After you have read the list, run it with the digest of that list; `--backup-tested` is your statement that the 1.x backup was made and its restore was tested (the command cannot check that). It drops the triggers, views, tables, functions, sequences and the schema in one transaction, then the roles of `ledger.import.source.roles`; a role that is still in use stays and is listed as `SKIPPED`. The ledger never runs this by itself.

```sh
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar retire-1x --ledger.import.source.username=<owner-account>
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar retire-1x --ledger.import.source.username=<owner-account> --confirm=<sha256> --backup-tested
```

### New

- The fifteen structured read tools, with `max_rows`, `cursor`, `truncated` and `next_cursor` on the lists, plus first-class `spec`, `deliverable`, and `session_token` support across all domains.
- `notifications/tools/list_changed`: a change of a common code reaches connected clients without a restart.
- The history keeps the full row as it was before a change (`before_data`, returned with `include_before`).
- Specification and task ids are assigned by the server when none is given.
- Attachments: the body of a review report or of other evidence is kept outside the database, encrypted and never changed. The five tools `artifact_begin` (with a required `operationKey`), `artifact_chunk`, `artifact_finish`, `artifact_status` and `artifact_read` upload and read multi-file bundles; `ledger_transition`, `ledger_review`, `ledger_review_correct`, `ledger_correct`, `ledger_record_deliverable`, `ledger_record_case` and the operations of `ledger_batch` take an optional `attachment_id` that a history row keeps (the history output returns it). The eleven settings `ledger.attachments.directory`, `key-directory`, `active-key-id`, `max-file-bytes`, `staging-budget-bytes`, `attachment-budget-bytes`, `max-open-per-owner`, `disk-margin-bytes`, `upload-ttl`, `orphan-grace` and `reaper-interval` are described in the README (Configuration); the commands `attachments-check`, `attachments-rekey`, `attachments-key-create`, `attachments-prepare` and `attachments-send` check, re-encrypt, rotate and stream local files directly. Back up the attachment directory, the key directory and the database together and run `attachments-check` after a restore. The tables are `upload_staging`, `attachment` and `attachment_file` (schema file `V8__attachments.sql`). 1.x evidence stays as the URI and digest it was recorded with; the import fetches nothing.
- One hook jar, `ledger-client-hook.jar`, for Claude Code, Codex and Antigravity (`clients/claude`, `clients/codex`, `clients/antigravity`), with Ed25519 session keys, plus vendor-independent HTTP `Bearer` session tokens (`token-issue`, `token-revoke`, `token-list`).
- The admin web is server rendered, signs in with the admin token (`ledger.admin.sign-in=token`), with OpenID Connect for one e-mail address (`ledger.admin.sign-in=oidc`, `ledger.admin.oidc.owner-email`) or with a passkey, approves every change with a passkey (Spring Security's WebAuthn support, user verification required, the challenge made from the change and the session, used once), and registers the JDBC driver (`ledger.admin.driver-directory`). The passkeys are kept in the ledger database (V7, no BLOB, insert-only history).
- `ledger-cli` with twenty-six commands, among them `attachments-check`, `attachments-rekey`, `attachments-key-create`, `attachments-prepare` and `attachments-send` (see Attachments above), `token-issue`, `token-revoke` and `token-list`, `passkey-code` (the one-time code that enrols a passkey, `--remove-existing` to reset), `driver-register`, `migrate`, `key-register`, `key-revoke`, `mcp-check`, `token-generate`, `render-deploy` and `prepare-host`. `secret-set`, `migrate` and `setup` take `--stdin` (the convention of `docker login --password-stdin`: the secret is the first line of standard input, never an argument or an environment value), `secret-set` takes `--if-absent`, and `token-generate` takes `--copy-to=<name>`.
- The migration tool `ledger-migrate-1x.jar`, the module `ledger-migrate-1x`, built next to the other jars and kept in the same folder; the installers do not know it and do not copy it. It is run as `java -jar dist/ledger-migrate-1x.jar <command>` and has four commands. `stop-1x` stops and disables the 1.x services `<name>` and `<name>-admin` and keeps each definition as `<unit>.1x-backup`; 1.x ran on Linux with systemd only, so `--platform=windows` is refused with `NO_1X_SERVICE_WINDOWS`; it runs `systemctl` with fixed arguments, because Java has no API for the service manager, and touches only a service of 1.x with that name; with `--env=<file>` it tells the public host names of the 1.x environment file that the one `--mcp-host` and the one `--admin-host` do not carry, as names that 2.0 no longer accepts. `import-secrets-1x` moves the two tokens of the 1.x environment file into the secret store (`--replace` replaces the tokens that the installer generated; the file is given with `--env=<file>` or on standard input with `--stdin`). `import-1x` copies the 1.x ledger and `retire-1x` removes what the 1.x installer made in the database, after you accept 2.0, only on your confirmation. Their settings are `ledger.import.source.*`; the README (Upgrading from 1.x) has the procedure.
- `prepare-host` does in Java what the installers did with operating system commands (`install -d`, `install -m`, `mkdir`, `icacls`, `copy`): the folders with owner and mode or ACL, the copies of the jars, the driver and WinSW. On Windows it closes the home to every account but SYSTEM and Administrators and gives LocalService its access in the same step; the folders of the secrets are made with an ACL for the installing user (everything) and LocalService (read only), and nothing is handed over to LocalService (there is no `seal-host`; the installing user stays the owner and no privilege to take ownership is used). The secrets that the secret store and the key setup create get the same two entries.
- Two installers that start only what Java cannot do (`useradd`, `runuser`, `systemctl`, WinSW, `sc.exe`) and leave the rest to `ledger-cli`: `deploy/install.sh` (Linux, systemd) and `deploy\install.cmd` (Windows, services registered with WinSW). They serve a personal PC, a Windows server and a Linux server; macOS is not supported. `--name=<name>` gives an instance of its own: the services are `<name>` and `<name>-admin`, and the Linux user, the directories and the WinSW ids follow the name, so two instances (or an instance next to a host that still runs 1.x) can live on one host with their own ports; Java validates the name before anything is created. Both servers run as one service account that belongs to no person (`pg-ledger-mcp` on Linux, LocalService on Windows), and the secret directory is readable by it alone.
- Two database accounts: the application account, which `migrate --app-account=<account>` gives the least privilege of `dml-grants.sql` (ANSI `GRANT` only, no DDL, no `UPDATE` or `DELETE` on the history), and the DDL account of `migrate --owner-account=<account>`, whose password is typed with hidden input and never stored.
- The settings of an installation live in one directory (`ledger.secrets.home`): `application.yaml` and one file per service, rendered by the installer, and `local.yaml` for your own settings, which is never replaced.
- `token-generate` makes the bearer and admin tokens from 32 bytes of a `SecureRandom` and keeps an existing token on a re-run.
- Schema files `V{n}__*.sql` and the history table `schema_history`, applied by `migrate`; a changed file stops `migrate` before it applies anything and every process at start. The history table has one row for each attempt of a version (`version`, `attempt`, `script`, `digest`, `applied_at`, `outcome` `SUCCEEDED` or `FAILED`, the form that the three products share); an attempt is one transaction, and two `migrate` runs at the same time are safe (the second waits in the database and skips what the first applied). The long text type of the schema files is declared by the dialect of `SqlBuilder`, which `migrate` takes from the product name of the connection, so there is no setting and no installer option for it, and the database encoding must be UTF-8: before it changes anything, `migrate` sends a text of three characters (two Korean letters and an emoji) through a probe query that the same dialect writes for each product and refuses to go on (`SCHEMA_ENCODING_NOT_UTF8`) when the database gives back another length or another text, so the list of character sets of the database is not read and no name of a character set is compared. The ledger does not use Flyway (it needs a module for each DBMS) and migrates by `ledger-cli migrate`, because the servers do not hold the DDL password.
- `setup`, the first setup of the ledger database: it migrates as `migrate` does, checks that the application account can use the schema (exit code `3` and the missing step when it cannot), adds the seed codes that are missing through the service of `code-set` and compares the seed with the database by counts and a SHA-256 digest. Running it again changes nothing. The installers call it.
- The seed bundle `ledger-seed.mv.db` in `ledger-cli.jar`, written by the build from `src/seed/issue-categories.tsv` and `src/seed/install-defaults.properties` (the module `ledger-seed`): the 14 default defect categories and the defaults of an installation. It is H2 data only; the ledger is always kept by the database system that you install, and the registration of an H2 driver or of a JDBC URL of H2 is refused. Only `ledger-cli` carries the H2 driver; the MCP server and the admin web keep none.
- `install-default <name>`: the defaults of an installation (`instance-name`, `mcp-port`, `admin-port`) are written once, in the seed bundle, and `render-deploy`, `prepare-host`, `mcp-check` and the two installers take them from it.
- The personal edition: one person installs the product on their own computer or on a server of their own and trusts the whole installation target. The MCP server and the admin web listen on `127.0.0.1` only, fixed in the code of both (there is no setting for the address, and `server.address` has no effect); the actuator shares the port of the server (`/healthz`), and a service whose `management.server.port` differs from its `server.port` does not start (`MANAGEMENT_PORT_SEPARATE`), because that second listener would not be bound to loopback. Reaching them from another machine, with a reverse proxy and a TLS certificate, is the operator's, with a tool of the operator's choice: the installers write no proxy configuration, order no certificate and install no renewal timer.
- `--mcp-host` and `--admin-host` take one host name each (the name that the operator's reverse proxy passes in the `Host` header), and either can be given without the other. The `Host` check of a service allows that name besides `127.0.0.1` and `localhost`, which are always allowed; with `--admin-host` the installer also writes the passkey settings for the name.
- Deploy settings: `ledger.admin.agent-token` is required and must differ from `ledger.admin.token`; `ledger.admin.lockout.global-delay` slows credential checks once more than a budget of them arrive within a window (it never locks or refuses; defect D-0013: a lock per client address locked the owner out behind the operator's proxy, so the settings `ledger.admin.lockout.max-failures` and `ledger.admin.lockout.lock-period` do not exist).

### Changed

- The rules that PostgreSQL functions and triggers enforced (grants, state transitions, same-session refusal, receipts, id assignment, creation provenance) are enforced by the application services with the same error tokens.
- The history has no update or delete path in the application; the grant template of the database module (`dml-grants.sql`) gives the application account no `UPDATE` or `DELETE` on it.
- Times are UTC everywhere; the admin web shows them in the local time of the browser.
- The license changes from the MIT License to the GNU Affero General Public License v3.0 or (at your option) any later version (`AGPL-3.0-or-later`) from 2.0.0; `LICENSE` holds the unmodified GNU AGPL v3 text, and the choice of later versions is stated in the README. `AGPL-3.0-or-later` applies to 2.0.0 and to every release published after it, including any later maintenance release of the 1.x line; the MIT License continues to apply only to the copies already published under it, that is v1.0.0 and v1.1.0. Under section 13, whoever runs a modified version as a network service must offer its users the corresponding source code. The admin web shows a link to the source code in its footer; its address is the setting `ledger.source.url` (default: the public repository of the project), which whoever runs a modified version points at the place where the source of that version is offered.
- The MCP server and the admin web run as one service account and never as root.
- The installers call `setup` where they called `migrate` before. The files that `render-deploy` writes are byte for byte the same for the same options; only the place of the defaults changed.
- The line of `setup` that compares the seed with the database says what a code that differs from the seed is: it differs and was kept, because the operator changed it or `import-1x` took it from 1.x. The counts and the exit codes did not change.
- The MCP server logs no `Replace existing Tool` WARN at its start: the annotation scanner of Spring AI is off (`spring.ai.mcp.server.annotation-scanner.enabled`), so the catalog is the only one that registers the tools, with its own definitions. The tool names, keys and results did not change, and the level of the logger of the SDK is not lowered.
- A relation between two issues keeps its direction where the kind has one. 1.x stored every relation with its smaller id first, so `caused_by` (a is caused by b) and `blocks` (a blocks b) lost which issue is the subject. The direction is now a property of the code of the relation kind (`common_code.direction`: `GIVEN` keeps `a` and `b` as the caller gave them, `CANONICAL` keeps the canonical order, so (a, b) and (b, a) are one relation); `caused_by` and `blocks` are `GIVEN`, and a kind added with `code-set --direction=<direction>` or in the admin console declares its own. `ledger_issue` reports the end (`a` or `b`) that the issue is, `ledger_codes` reports the direction, and the `ledger_link` definition marks the directed kinds. The check `CHECK (a < b)` of the relation table `issue_relation` is `CHECK (a <> b)` (schema file `V4__relation_direction.sql`).
- `import-1x` cannot restore the direction of a `caused_by` or `blocks` relation of 1.x, because 1.x kept nowhere which issue the caller named first. It imports them as stored (nothing is guessed) and lists them: the count and the ids, also in the audit row and with `--verify-only`. Check them and, where one is the wrong way round, remove it and link it again with `ledger_link`.
- A file that an installer did not render and that a rendered file replaces is kept as `<file>.backup`.
- The history entries that come from another ledger use the neutral names `IMPORTED_*` (the operations `IMPORT`, `IMPORTED_NOTE` and `IMPORTED_CHANGE`, the assurances `IMPORTED_LOGIN`, `IMPORTED_SHARED` and `IMPORTED_UNKNOWN`) and the field `source_ref` in the read tools; `import-1x` maps the values of 1.x to them. The write tools have no `author_id` argument; the author is the verified caller.
- Four rules of the write tools are stricter. A `VERIFIED` entity takes no `ledger_record_deliverable` and no edit (`VERIFIED_ENTITY`); a reviewer reopens it first with `ledger_review`. An issue is verified only by a session that did not register it, did not record a case of it and did not record or amend a deliverable of it, a specification or task only by a session that did not create it, does not own it, never recorded a deliverable on it and never reported it completed, and a milestone criterion is set `MET` or `NOT_MET` only by a session that did not register or complete it (`SAME_SESSION`; the cases and the registrants of merged issues count as its own). An explicit issue id, or spec or task id of the form `<CODE>-S-0001` or `<CODE>-T-0001`, must have a number up to the next number of the project: a larger number is refused with `ID_NUMBER_AHEAD` (`ID_COUNTER_CHANGED` asks you to send the request again when another request took the number meanwhile), and such an id is stored only as the server writes it (`<CODE>-D-00002` and the number 0 are refused with `VALIDATION_FAILED` at `id`). `ledger_link` and a merge into an issue of another project need the matching grant on both projects.
- The command line tool finds the installation where the installer of the host puts it, without an option: `ledger.secrets.home` defaults to `/etc/<name>` on Linux and to `C:/ProgramData/<name>/etc` on Windows (defect D-0089). Every program (the command line tool, the MCP server, the admin web, the migration tool) sets the time zone of its own JVM to UTC when it starts, so a command needs no `-Duser.timezone=UTC` on a host whose zone is not UTC (defect D-0090). What depends on the kind of the file system (POSIX permissions, ACLs, DOS attributes) is decided in one module, `ledger-files` (defects D-0091, D-0092); the Linux calls of `stop-1x` are one class, `SystemdServices`, that takes the paths of `DeployLayout` (defect D-0093); a `prepare-host` that fails puts the modes and owners of the directories back on Linux as it already did the ACLs on Windows (defect D-0094). The key store of the hook names the account of the process as the server and the command line tool do (`DOMAIN\name` on Windows, not `user.name`), a file is never moved over a file of the same name in the attachment folder, `install.cmd` reads the state of a service from the number of `sc.exe query` and not from a word that is in the language of the machine, and the README says how Windows PowerShell 5.1 encodes a secret piped with `--stdin` (defect D-0095).
- Only a write that stores the category or the severity (`ledger_issue_save`) checks those common codes. State changes do not, so an imported issue that still holds the retired severity `UNRATED` can be progressed, verified and merged, and is rated by an edit.

### Removed

- DBHub, Node and the Node hook scripts, replaced by the Java server, the Java admin web and the hook jar.
- The PostgreSQL functions, triggers and login roles of 1.x; the author and reviewer logins are now the channels of the tools.
- The tools `execute_sql_reader` and `search_objects_reader`.
- The environment file with secrets. The 1.x shell installers, the unit templates and the domain automation of `deploy/` are replaced by the two installers and removed; the history of the repository keeps them.
- The 1.x implementation that was kept in the tree during the development of 2.0 (`bin/`, `web/`, `mcp/`, `sql/` and `tests/`): the source of 1.x is available at the tag `v1.1.0`.
- Every handling of 1.x in the 2.0 services, the installers and `ledger-cli`: no 1.x type, SQL, setting or environment file remains in them. The option `--from-1x-env=<file>` of the installers, `render-deploy` and `prepare-host` is gone, and so are the `ledger-cli` commands `secret-import-1x`, `import-legacy` and `retire-legacy`; the commands `import-secrets-1x`, `import-1x` and `retire-1x` of `ledger-migrate-1x.jar` replace them, and `stop-1x` replaces stopping the 1.x services yourself.
- The conflict code `REQUEST_ID_LEGACY` and the receipts that were imported from 1.x: `import-1x` copies no request receipt.

### Security

- Defect D-0012 is fixed: 1.x did not verify `_hostAttestation`, so a holder of the bearer token could write under the name of another session. The server now verifies an Ed25519 signature made with a key that the owner registered for the author and the server, and checks the tool, the operation key, the arguments and the time (`ledger.attestation.window`).
- A signature made for one server never verifies on another, and a missing key is not told apart from a wrong signature.
- The admin web refuses the token of the agents (`AGENT_TOKEN_FORBIDDEN`), slows down many credential checks without ever locking or refusing the right credential (`ledger.admin.lockout.*`, defect D-0013), and uses CSRF tokens and a `Secure`, `SameSite=Strict` session cookie.
- Secrets are read from the secret store with hidden input and are never printed (a token is shown once, by `token-generate --print`, when it is created). The secret directory is owner-only (POSIX permissions, or an ACL on Windows) and readable by the service account alone (on Windows: by the installing user and, read only, by LocalService), which separates the secrets of the ledger from the account of the person and of the agents. The secrets are kept in one folder per use (`common`, `admin`, `mcp`, `tool`), and each service and tool imports only the folders it needs as configuration trees of their own (defect D-0031): the MCP server no longer has the admin token or the OpenID Connect client secret in its `Environment`. The key files of the attachments are in `<settings folder>/attachment-keys`, below no configuration tree (Spring Boot makes every file below a tree a property of the process). The two services run as one operating system user, so the file permissions do not keep one from reading the folder of the other.
- The database password of the DDL account is typed for one run and is never stored; the application account has no DDL right and no `UPDATE` or `DELETE` on the history.

### Requirements

- A Java 25 runtime on the hosts of the MCP server and the admin web (at a path that every account can execute, not under `/home`, because the service account runs it too; `deploy/install.sh` takes `--java=<path>` and checks it), and on every client host for the hook jar (class file version 69.0; an older JVM refuses it with `UnsupportedClassVersionError`). The build needs JDK 25.
- Linux with systemd, or Windows with the WinSW 2.x executable, which you obtain yourself like the JDBC driver; the installers bundle and download nothing.
- A JDBC driver of your choice, obtained by you and registered with `driver-register`; the product bundles none. A database whose session time zone is UTC, that uses UTF-8 and that compares text case-sensitively. PostgreSQL is the database that is tested; other products are not tested.
- To reach the servers from outside: a reverse proxy and a TLS certificate of the operator's choice on the same host, which passes the `Host` header on (the proxy keeps long MCP connections open); the installers do not provide them.
- To move a 1.x installation: the jar `ledger-migrate-1x.jar` (built with the other jars, a Java 25 runtime) and, for `stop-1x`, root with `systemctl` (the host of 1.x is a Linux host). The 1.x ledger must be complete up to its last installer step (observed cases, common codes and creation provenance); otherwise `import-1x` refuses. `import-1x` reads the 1.x ledger, which is a PostgreSQL database.
- Clock of the client hosts and of the server within `ledger.attestation.window` (five minutes by default).

### Known limitations

- macOS is not supported.
- The file protection and the installer name the built-in Windows accounts (`NT AUTHORITY\LocalService`, `NT AUTHORITY\SYSTEM`, `BUILTIN\Administrators`) by their English names, because the JDK cannot look an account up by its SID; a Windows in a language whose names differ was not tried. `--java` and `--home` accept plain path segments only (on Windows `--java` also a space), so a path with parentheses (`Program Files (x86)`) or letters outside ASCII is refused, and `install.cmd` takes the `java` of the `PATH`.
- Direct file streaming from the PC outside the model context uses `ledger-cli attachments-prepare` and `ledger-cli attachments-send` after `artifact_begin` and before `artifact_finish`.
- A text that identifies a row and is empty in the 1.x ledger (the release or the code of a condition, the repository of a fix, a title) is not stored as NULL: `import-1x` lists it and writes nothing, and the row has to be corrected in the 1.x ledger. The empty texts of the five long text columns are imported (see above).
- `driver-register` writes the registration file even when the schema of the ledger database is not migrated yet (a first installation, or a rerun after the schema was dropped), and says that the row of the owner's audit trail is still to come; `migrate` and `setup` record it, once, when the schema is ready.
- On Windows, run the installer again as the same user: the secrets are the installing user's (with read for LocalService).
- The privilege to use a schema is a statement of the database system and not part of the product SQL: `setup` checks it and stops with exit code `3` when the application account lacks it; an operator gives it, and `setup` continues where it stopped. `setup` never changes a code that exists, so a later version that changes a code of the seed does not change it in an existing ledger; use `code-set` for that.
- `deploy\install.cmd`, like `install.sh`, takes `--stdin` (as its first argument) to read the passwords from standard input, so an installation on Windows needs no person at the terminal. Creating the operating system user, switching to it, and the service managers stay in the scripts because Java has no API for them. Changing the folders needs root, or an elevated prompt on Windows, and there is no probe: Java refuses with `HOST_FAILED`.
- On Windows the secrets are not handed over to the service account: the installing user owns them and LocalService reads them, so the owner commands of `ledger-cli` keep working for the installing user (the admin web is the other place of the owner work).
- Another process of the same operating system user can read the session key file; isolation inside one user needs separate accounts.
- The personal edition trusts the whole PC: the hook and the command line read an existing key folder, key file or secret whoever may reach it, whoever owns it, and through a link; they create new ones owner-only. Only a path of the wrong kind (a directory where a file belongs) and an empty file are refused.
- A signed token that is replayed inside the time window can only repeat the same call (receipt idempotency), never carry other content; the window is not a one-time token.
- The MCP server, the admin web and the owner commands share one application account (the service account separates the secrets, not the rights in the database), so a compromised MCP server process holds the right to write the session keys and the grants as well.

## 한국어

### 요약

2.0.0은 1.x 구현(DBHub, Node, PostgreSQL 함수와 트리거, 원시 SQL 도구)을 Java 25와 Spring Boot 4.1로 작성한 범용 장부로 대체합니다. 소프트웨어 개발, 영화 제작, 집필, 연구, 운영 전반에 걸쳐 이슈, 명세, 작업, 마일스톤 기준, 산출물과 독립 검수를 기록합니다. 모든 MCP 응답은 `ApiResult.v1` 봉투(`schemaVersion` `"1.0.0"`, `ok`, `data`, `error`)를 쓰며, 모든 쓰기 도구는 평탄하고 검증된 인자와 필수 `operationKey`를 받고, 호출자는 표준 작성자별 HTTP `Bearer` 세션 토큰(`STANDARD` `ledger.mcp.auth-mode`에서 `token-issue`가 발급하는 `lgt_...`) 또는 Ed25519 `_hostAttestation` 토큰으로 인증합니다. SQL은 ANSI이며 DBMS 고유 기능은 사용하지 않습니다. JDBC 드라이버는 사용자가 붙이며 동봉하지 않고, 제품마다 다른 세 곳인 목록의 행 수 제한, 긴 텍스트 열 타입의 선언, 데이터베이스의 인코딩을 확인하는 탐침은 `SqlBuilder`가 고릅니다. 이 판에서 시험하는 데이터베이스는 PostgreSQL입니다. 다른 제품도 동작할 수 있으나 시험하지 않았고 이 세 곳 밖에서는 제품별 맞춤이 없습니다. 시각은 UTC로 저장하고 전송합니다. 2.0 자체에는 1.x를 다루는 코드가 없습니다. 서비스, 설치기, `ledger-cli`는 1.x의 설정, 파일, 표를 읽지 않습니다. 기존 1.x 설치는 별도의 도구 `ledger-migrate-1x.jar`가 옮기며, 명령은 `stop-1x`, `import-secrets-1x`, `import-1x`, `retire-1x` 네 개입니다.

### 호환되지 않는 변경

1. **결과 감싸기가 `ApiResult.v1`으로 교체되었습니다.** DBHub는 쓰기 결과를 `rows[0].result`로 감쌌습니다. 이제 모든 도구는 `ApiResult.v1`(`schemaVersion`, `ok`, `data`, `error`)을 반환하며 페이로드 키(`status`, `entity`, `id`, `version`, `history_id` 등)가 `data` 안에 들어 있습니다. `rows[0].result`를 읽던 클라이언트는 `data`에서 읽어야 합니다.
2. **원시 SQL 도구 제거.** `execute_sql_reader`와 `search_objects_reader`는 더 이상 없습니다. 정형 읽기 도구 15종 `ledger_get`, `ledger_issue`, `ledger_spec`, `ledger_task`, `ledger_criterion`, `ledger_history`, `ledger_search`, `ledger_issues`, `ledger_specs`, `ledger_tasks`, `ledger_criteria`, `ledger_attention`, `ledger_stats`, `ledger_projects`, `ledger_codes`가 이를 대체합니다. 스키마를 직접 읽던 질의에는 대응하는 도구가 없습니다.
3. **호출자 인증과 `_hostAttestation`의 값이 바뀌었습니다.** 기본값인 `STANDARD` `ledger.mcp.auth-mode`에서는 작성자별 `Bearer` 세션 토큰(`lgt_...`)만으로 `_hostAttestation` 없이 인증할 수 있습니다. `_hostAttestation`을 쓸 때 `<vendor>:<session-id>`만 있는 값은 `ATTESTATION_UNSIGNED`로 거절됩니다. 새 값은 `pgla2.<author>.<tool>.<operation key>.<arguments digest>.<issued at>.<signature>`이며, 인자의 RFC 8785 정규형의 SHA-256까지 덮는 Ed25519 서명입니다. 작업 키는 호출의 `operationKey` 인자입니다. 새 훅 jar만 이 값을 만듭니다.
4. **기존 부여에는 세션 키나 세션 토큰이 필요합니다.** `import-1x`는 옛 부여를 키 없이 복사하므로, 소유자가 `key-register`로 세션 키를 등록하거나 `token-issue`로 세션 토큰을 발급하기 전까지 가져온 작성자의 쓰기는 `ATTESTATION_SIGNATURE_INVALID`로 거절됩니다. 등록하면 그 부여는 이전처럼 동작합니다.
5. **1.x 요청 영수증은 가져오지 않습니다.** `import-1x`는 영수증을 복사하지 않습니다. 2.0의 모든 쓰기는 `operationKey`를 요구하고 옛 `request_id`는 알 수 없는 인자로 거절하므로, `request_id`로 재시도하는 1.x 클라이언트는 거절되어 아무것도 기록하지 않습니다. 1.x에서 응답이 유실된 요청이 2.0에서 두 번째 쓰기를 일으킬 수 없습니다. 1.x 이력 행의 `request_id`는 `operation_key`로 보존됩니다. `REQUEST_ID_LEGACY`는 제거되었습니다. 작업 키는 일반 규칙에 따라 중복으로만 거절됩니다(`OPERATION_CONFLICT`).
6. **설정이 옮겨졌습니다.** 1.x의 환경 파일은 없어졌습니다. 비밀은 `secret-set`으로 저장하고, 배포 설정은 README에 나열한 Spring Boot 속성입니다. 1.x 환경 파일의 에이전트 토큰은 `import-secrets-1x`가 비밀 저장소로 옮기며, 관리 토큰은 옮기지 않습니다(설치기가 `token-generate`로 2.0의 것을 만듭니다).
7. **관리 웹은 관리 토큰, OpenID Connect 또는 패스키로 로그인하고, 모든 변경을 패스키로 승인합니다.** 관리 토큰은 `ledger.admin.sign-in=token`일 때만 브라우저를 로그인시키며(개인판이고, 읽기 전용 JSON 엔드포인트의 bearer로도 남습니다), `oidc`나 `passkey`이면 로그인 페이지에 토큰 입력란이 없습니다. 로그인은 `ledger.admin.sign-in`(`token`, `oidc`, `passkey` 중 정확히 하나이며 기본값은 `passkey`)으로 고르며, `ledger.admin.oidc.*` 설정이 있는데 선택이 없는 설치는 시작할 때 거절됩니다. OpenID Connect의 소유자는 발급자 `ledger.admin.oidc.issuer`의 이메일 주소 하나인 `ledger.admin.oidc.owner-email`입니다. 첫 패스키는 `ledger-cli passkey-code`의 일회용 코드로 등록합니다.
8. **쓰기 도구의 입력이 평탄화·검증되었으며 옛 형식은 받지 않습니다.** 개체별 평탄화 도구(`ledger_issue_save`, `ledger_spec_save`, `ledger_task_save`, `ledger_criterion_save`, `ledger_transition`, `ledger_record_deliverable`, `ledger_record_case`, `ledger_link`, `ledger_correct`, `ledger_review`, `ledger_review_correct`, `ledger_batch`)가 다형 맵을 대체하며 `request_id`와 `batch_request_id`를 대신하는 필수 인자 `operationKey`(1자 이상 128자 이하, 예를 들어 UUID)를 받습니다. 같은 키에 같은 인자는 저장된 답을 돌려주며 한 번만 기록하고, 같은 작성자의 같은 키에 다른 인자는 `OPERATION_CONFLICT`이며(`artifact_begin`의 키와 같아 다른 작성자는 같은 키를 쓸 수 있습니다), 키가 없거나 비어 있으면 `VALIDATION_FAILED`(경로 `operationKey`)입니다. 서버는 키를 대신 만들지 않고 훅도 넣지 않습니다. `ledger_batch`는 배치에 키 하나를 받으며 그 연산에는 키가 없습니다. 배치는 하나의 요청이므로 같은 키에 다른 연산이거나 다른 도구이면 `OPERATION_CONFLICT`입니다. 선택 필드의 JSON `null`은 생략한 것으로 보며, 선택 텍스트 필드는 빈 텍스트로 지웁니다. `artifact_chunk`와 `artifact_finish`는 `operationKey`를 받지 않습니다(업로드는 `artifact_begin`의 `operationKey`로 시작하고, 청크는 `uploadId`, `sequence`, `chunkSha256`으로, finish는 `attachmentId`로 멱등입니다). `author_id` 인자는 없어졌습니다. 객체나 배열 인자는 문자열에 담은 JSON 문서가 아니라 그 JSON 값으로 보내야 하며, 텍스트 `null`은 인자가 없다는 뜻이 아니라 하나의 텍스트입니다. `request_id`, `batch_request_id`, `author_id`를 포함해 알 수 없는 인자는 거절됩니다. 이력의 `request_id` 열은 `operation_key`이고 이력의 출력 필드도 `operation_key`입니다.

### 이전 절차

1. 먼저 모든 클라이언트 호스트에 훅 jar를 설치하고 `PATH`에 Java 25 런타임을 둡니다. 서명하는 훅이 없는 쓰기는 `HOST_ATTESTATION_REQUIRED`로 거절됩니다.
2. 백업하고 1.x 서비스를 멈춥니다. DBMS의 덤프 도구로 장부 데이터베이스를 백업하고 `/etc/pg-ledger-mcp`(1.x 파일 `/etc/pg-ledger-mcp/env`에 1.x의
   비밀이 있습니다)와 1.x 유닛 파일을 복사해 둡니다. 그런 다음 1.x 호스트에서 root로 `stop-1x`를 실행합니다. 서비스 `<name>`과 `<name>-admin`(기본 이름은 `pg-ledger-mcp`)을 멈추고
   비활성화하며 각 정의를 백업으로 보관합니다. 유닛 파일이 `<unit>.1x-backup`으로 옮겨집니다(1.x에는 Linux의 systemd 유닛 설치만 있었으므로 `--platform=windows`는 `NO_1X_SERVICE_WINDOWS`로 거절합니다).
   Java에는 서비스 관리자를 다루는 API가 없으므로 명령은 고정된 인자로 `systemctl`을 실행하며, 이름이 같고 정의가 1.x의 것인 서비스만 건드립니다
   (그렇지 않으면 `NOT_1X_SERVICE`이며 아무것도 바꾸지 않습니다). 1.x의 공개 호스트 이름은 조용히 사라지지 않습니다. `--env=<file>`을 주면 명령은 1.x의 `DBHUB_ALLOWED_HOSTS`(1.1.0은 `PGLEDGER_ADMIN_ALLOWED_HOSTS`도)가
   허용하는 호스트 이름을 읽고, 아무것도 멈추기 전에 설치기에 줄 하나의 `--mcp-host`(또는 `--admin-host`)가 담지 않은 공개 호스트 이름을 2.0이 더는 받지 않는 이름으로 알립니다(설치기는 서비스마다 호스트 이름 하나를 받습니다). 이를 이유로 거절하지는 않습니다.
   그 이름은 `--mcp-host=<name>`으로 줍니다. 다시 실행할 수 있으며, 1.x로 되돌리는 방법을 출력합니다.

```sh
sudo java -jar dist/ledger-migrate-1x.jar stop-1x --env=/etc/pg-ledger-mcp/env --mcp-host=<mcp-host> --admin-host=<admin-host>
```

3. DBMS의 도구로 데이터베이스 계정 둘(앱 계정과 DDL 계정)을 만들고, JDBC 드라이버를 직접 구한 뒤, 호스트의 설치기로 2.0.0 jar를 설치합니다. 설치기는 1.x를 알지 못하며, `--mcp-host`와 `--admin-host`에는 2단계와 같은 호스트 이름을 줍니다.
   1.x 스키마는 변경하지 않고 읽기만 합니다. 설치기가 비밀을 저장하고(`secret-set`, `token-generate`), 드라이버를 등록하고, `migrate`로 스키마를 만들고, `dml-grants.sql`을 앱 계정에
   적용하고, 두 서비스를 시작합니다. 설치기가 렌더하지 않은 파일을 렌더한 파일이 대체하면 그 파일은 `<file>.backup`으로 보관합니다. 세 대상(개인 PC, Windows 서버, Linux 서버)은 README(설치)에 설명되어 있습니다.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url>
```

```bat
deploy\install.cmd dist <winsw-exe> <driver-jar> <driver-class> <ddl-account> <app-account> "<jdbc-url>"
```

4. 설치기를 마친 뒤 `import-secrets-1x`로 1.x의 비밀을 옮깁니다. 비밀 저장소는 서비스 계정의 것이므로, root가 1.x 파일을 열어 표준 입력으로 도구에 넘기고 도구는 서비스 사용자로 실행합니다.
   설치기가 자체 토큰을 생성했으므로 `--replace`가 그 토큰을 1.x의 값으로 대체하며, 그러면 클라이언트가 그대로 동작합니다(1.x의 관리 토큰은 가져오지 않으므로 관리 웹은 설치기가 만든 관리 토큰으로 로그인합니다). 값은 출력하지 않으며 `--replace`가 없으면 이미 있는 비밀은 그대로 둡니다.
   그런 다음 `sudo systemctl restart pg-ledger-mcp pg-ledger-mcp-admin`으로 2.0.0의 두 서비스를 재시작합니다.

```sh
sudo sh -c 'runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar import-secrets-1x --replace --stdin < /etc/pg-ledger-mcp/env'
```

| 1.x 환경 값 | 2.0.0 비밀 |
|---|---|
| `DBHUB_AUTH_TOKEN` | `ledger.mcp.token`이며, 같은 값을 `ledger.admin.agent-token`에도 사용합니다 |
| `PGLEDGER_ADMIN_TOKEN` | 가져오지 않습니다. 설치기가 `token-generate`로 만든 `ledger.admin.token`이 2.0의 관리 토큰입니다(사람이 정한 토큰은 더 약할 수 있으며, 1.x 환경에 이 설정이 있으면 명령이 그 사실을 알립니다) |
| 장부 로그인의 데이터베이스 비밀번호 | `ledger.jdbc.password`이며, 설치기가 앱 계정의 것을 입력받습니다 |

5. `migrate`와 `setup`이 만든 스키마(`setup`을 실행하는 설치기를 마친 상태)에 `import-1x`로 1.x 장부를 한 번 가져옵니다. 가져오기는 1.x 스키마를 읽기 전용으로 읽어 모든 행을 한 트랜잭션으로 복사하고, 모든 표의 행 수와 SHA-256 다이제스트를 대조합니다. `--verify-only`는 대조만 다시 합니다. `setup`이 쓴 시드 코드와 감사 행은 받아들이고(1.x에도 있는 시드 코드는 1.x의 값을 따릅니다), 원장 데이터 표, 세션 키, 이전 가져오기 중 하나라도 이미 있으면 거부하며, 새 스키마가 담을 수 없는 값(공백이 있는 ID, 대소문자만 다른 ID 쌍, 칸보다 긴 텍스트)은 아무것도 쓰지 않은 채 모두 나열합니다. 해당 행을 1.x 장부에서 고친 뒤 다시 실행합니다. 1.x의 ID는 그대로 유지합니다. 작업이나 조건의 ID는 공백과 제어 문자가 없는 1자 이상 120자 이하이면 대소문자와 문자 종류(`:`, `/`, `#`, `.`, `_`, `-` 등)를 가리지 않으며, 결함 ID는 기존 형식(`<CODE>-D-0001`)을 그대로 씁니다. 같은 종류에서 대소문자만 다른 ID는 새 스키마에서 하나의 ID이므로(조회는 ID를 정확히 비교하고, ID를 대문자로 바꾼 키는 어떤 DBMS에서도 유일합니다) 가져오기는 그런 쌍을 거부하며, 작업이나 조건을 이미 있는 ID와 대소문자만 다르게 만들 수도 없습니다(`DUPLICATE_KEY`). 1.x의 빈 문자열(`purpose`, `success_condition`, `behavior`, `root_cause`, `condition_text`는 `''`를 허용했습니다)은 NULL로 저장하고 도구는 1.x처럼 빈 문자열을 돌려줍니다. 조건의 `code`(200자)와 `ci_ref`(2000자)는 이전 2.0 빌드보다 길어졌고, 작업의 `origin_ref`는 긴 텍스트(쓸 때 20000자까지)여서 1.x의 모든 값이 들어갑니다. 어떤 도구 스키마에도 ID의 패턴이 없습니다.

1.x의 요청 영수증은 복사하지 않습니다(호환되지 않는 변경 참조). 설정 `ledger.import.source.url`, `ledger.import.source.username`, `ledger.import.source.schema`와 비밀 `ledger.import.source.password`는 이 도구에 속하며, 명령은 서비스 사용자로 실행합니다.

```sh
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-cli.jar secret-set ledger.import.source.password
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar import-1x --owner-account=<ddl-account> --ledger.import.source.url=<jdbc-url> --ledger.import.source.username=<account>
```

6. 모든 작성자가 세션 키를 등록합니다. 세션이 공개 키와 지문을 출력하면, 소유자가 지문을 대조한 뒤 그 키가 만들어진 서버에 키를 등록하고, 그 작성자의 부여가 동작합니다.

```sh
java -jar ledger-client-hook.jar session-key <server> <author>
java -jar ledger-cli.jar key-register <author> <public-key-or-block> <fingerprint>
```

7. 클라이언트를 전환합니다. `execute_sql_reader`와 `search_objects_reader` 호출을 읽기 도구로 바꾸고, 쓰기 결과의 키는 결과 자체에서 읽습니다. `mcp-check`와 `import-1x --verify-only`로 서버를 확인합니다.
8. 되돌리려면 2.0.0 서비스를 멈추고, 각 `<unit>.1x-backup`을 원래 이름으로 되돌리고(백업이 남도록 복사합니다), `sudo systemctl daemon-reload`를 실행한 뒤 `sudo systemctl enable --now <name>`과 `<name>-admin`에 대한 같은 명령으로 1.x 서비스를 이전 설정으로 시작합니다. `stop-1x`가 이 절차를 출력합니다. 가져오기는 1.x 스키마를 변경하지 않습니다.
9. 2.0을 받아들이면 1.x 설치기가 데이터베이스에 만든 것을 제거합니다. 그때까지 보관한 유닛과 1.x 스키마가 되돌아갈 길이며, 어느 것도 그 전에 삭제하지 않습니다. 1.x 데이터베이스를 `pg_dump`로 백업하고 그 복원을 시험한 뒤 1.x 서비스를 멈추고, 1.x 객체를 소유한 계정(`ledger.import.source.username`)으로 `retire-1x`를 실행합니다. 옵션 없이 실행하면 2.0 장부가 1.x가 가졌던 것을 여전히 가지고 있는지(그 뒤 2.0이 추가하거나 고친 행은 받아들이며, `import-1x --verify-only`는 더 엄격해서 이를 차이로 보고합니다), 다른 세션이 1.x 스키마를 쓰고 있지 않은지 확인하고, 모든 객체를 제거 순서대로 보여 주며 그 목록의 SHA-256을 출력할 뿐 아무것도 바꾸지 않습니다. 목록을 읽은 뒤 그 목록의 다이제스트와 함께 실행합니다. `--backup-tested`는 1.x 백업을 만들었고 그 복원을 시험했다는 확인이며, 명령은 이를 확인할 수 없습니다. 트리거, 뷰, 표, 함수, 시퀀스, 스키마를 하나의 트랜잭션으로 제거한 다음 `ledger.import.source.roles`의 역할을 제거하며, 아직 쓰이는 역할은 남기고 `SKIPPED`로 표시합니다. 장부는 이 작업을 스스로 실행하지 않습니다.

```sh
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar retire-1x --ledger.import.source.username=<owner-account>
sudo runuser -u pg-ledger-mcp -- java -jar dist/ledger-migrate-1x.jar retire-1x --ledger.import.source.username=<owner-account> --confirm=<sha256> --backup-tested
```

### 추가

- 정형 읽기 도구 15종과 전 분야 `spec`, `deliverable`, `session_token` 지원. 목록 도구에는 `max_rows`, `cursor`, `truncated`, `next_cursor`가 있습니다.
- `notifications/tools/list_changed`: 공통코드가 바뀌면 연결된 클라이언트가 재시작 없이 반영합니다.
- 이력이 바뀌기 전의 전체 행을 보관합니다(`before_data`, `include_before`를 주면 반환됩니다).
- 명세와 작업 ID를 주지 않으면 서버가 부여합니다.
- 첨부: 검수 보고서나 그 밖의 근거의 본문을 데이터베이스 밖에 암호화해서 보관하며 바꾸지 않습니다. 도구 다섯 개 `artifact_begin`(필수 `operationKey`), `artifact_chunk`, `artifact_finish`, `artifact_status`, `artifact_read`로 다중 파일 번들을 올리고 읽습니다. `ledger_transition`, `ledger_review`, `ledger_review_correct`, `ledger_correct`, `ledger_record_deliverable`, `ledger_record_case`와 `ledger_batch`의 연산은 선택 인자 `attachment_id`를 받아 이력 행이 보관하며 이력 출력이 돌려줍니다. 설정 열한 개 `ledger.attachments.directory`, `key-directory`, `active-key-id`, `max-file-bytes`, `staging-budget-bytes`, `attachment-budget-bytes`, `max-open-per-owner`, `disk-margin-bytes`, `upload-ttl`, `orphan-grace`, `reaper-interval`은 README(설정)에 설명되어 있고, 명령 `attachments-check`, `attachments-rekey`, `attachments-key-create`, `attachments-prepare`, `attachments-send`가 점검, 재암호화, 키 교체 및 로컬 파일 직접 전송을 맡습니다. 첨부 폴더, 키 폴더, 데이터베이스를 함께 백업하고 복원한 뒤 `attachments-check`를 실행합니다. 표는 `upload_staging`, `attachment`, `attachment_file`입니다(스키마 파일 `V8__attachments.sql`). 1.x의 근거는 기록된 URI와 해시 그대로 남고, 이전은 아무것도 가져오지 않습니다.
- Claude Code, Codex, Antigravity가 함께 쓰는 훅 jar `ledger-client-hook.jar`(`clients/claude`, `clients/codex`, `clients/antigravity`)와 Ed25519 세션 키, 그리고 벤더 독립 HTTP `Bearer` 세션 토큰(`token-issue`, `token-revoke`, `token-list`).
- 관리 웹은 서버 렌더링이며, 관리 토큰(`ledger.admin.sign-in=token`), 이메일 주소 하나에 대한 OpenID Connect(`ledger.admin.sign-in=oidc`, `ledger.admin.oidc.owner-email`) 또는 패스키로 로그인하고, 모든 변경을 패스키로 승인하며(Spring Security의 WebAuthn 지원, 사용자 확인 필수, 변경과 세션으로 만든 challenge, 한 번만 사용), JDBC 드라이버를 등록합니다(`ledger.admin.driver-directory`). 패스키는 장부 데이터베이스에 저장합니다(V7, BLOB 없음, 추가만 하는 이력).
- 명령 26개를 가진 `ledger-cli`. `attachments-check`, `attachments-rekey`, `attachments-key-create`, `attachments-prepare`, `attachments-send`(위의 첨부 참조), `token-issue`, `token-revoke`, `token-list`, `passkey-code`(패스키를 등록하는 일회용 코드, `--remove-existing`은 초기화), `driver-register`, `migrate`, `key-register`, `key-revoke`, `mcp-check`, `token-generate`, `render-deploy`, `prepare-host` 등이 있습니다. `secret-set`, `migrate`, `setup`은 `--stdin`을 받고(`docker login --password-stdin`의 관례: 비밀은 표준 입력의 첫 줄이며 인수나 환경 변수로는 받지 않습니다), `secret-set`은 `--if-absent`를, `token-generate`는 `--copy-to=<name>`을 받습니다.
- 이전 도구 `ledger-migrate-1x.jar`(모듈 `ledger-migrate-1x`)는 다른 jar와 함께 빌드하여 같은 폴더에 두며, 설치기는 이 도구를 알지 못하고 복사하지도 않습니다. `java -jar dist/ledger-migrate-1x.jar <command>`로 실행하며 명령은 네 개입니다. `stop-1x`는 1.x 서비스 `<name>`과 `<name>-admin`을 멈추고 비활성화하며 각 정의를 `<unit>.1x-backup`으로 보관합니다. 1.x는 systemd가 있는 Linux에서만 실행되었으므로 `--platform=windows`는 `NO_1X_SERVICE_WINDOWS`로 거절합니다. Java에 서비스 관리자 API가 없으므로 고정된 인자로 `systemctl`을 실행하며, 그 이름의 1.x 서비스만 건드립니다. `--env=<file>`을 주면 1.x 환경 파일이 허용하는 공개 호스트 이름 가운데 하나의 `--mcp-host`와 하나의 `--admin-host`가 담지 않은 이름을 2.0이 더는 받지 않는 이름으로 알립니다. `import-secrets-1x`는 1.x 환경 파일의 토큰 두 개를 비밀 저장소로 옮깁니다(`--replace`는 설치기가 생성한 토큰을 대체하며, 파일은 `--env=<file>`로, 또는 `--stdin`으로 표준 입력에서 줍니다). `import-1x`는 1.x 장부를 복사하고, `retire-1x`는 2.0을 받아들인 뒤 1.x 설치기가 데이터베이스에 만든 것을 사용자가 확인할 때만 제거합니다. 설정은 `ledger.import.source.*`이며, 절차는 README(1.x에서 업그레이드)에 있습니다.
- `prepare-host`는 설치기가 운영체제 명령(`install -d`, `install -m`, `mkdir`, `icacls`, `copy`)으로 하던 일을 Java로 합니다. 소유자·모드 또는 ACL을 가진 폴더, jar·드라이버·WinSW의 복사입니다. Windows에서는 홈을 SYSTEM과 Administrators 외 모든 계정에게 닫고 같은 단계에서 LocalService에 필요한 접근을 주며, 비밀 폴더는 설치한 사용자(전체)와 LocalService(읽기만)의 ACL로 만듭니다. LocalService에 넘기는 것은 없습니다(`seal-host`가 없고, 설치한 사용자가 소유자로 남으며, 소유권을 가져오는 권한도 쓰지 않습니다). 비밀 저장소와 키 설정이 만드는 비밀도 같은 두 항목을 가집니다.
- Java가 할 수 없는 것(`useradd`, `runuser`, `systemctl`, WinSW, `sc.exe`)만 직접 실행하고 나머지는 `ledger-cli`에 맡기는 설치기 두 개: `deploy/install.sh`(Linux, systemd)와 `deploy\install.cmd`(Windows, WinSW로 서비스 등록). 개인 PC, Windows 서버, Linux 서버를 다루며 macOS는 지원하지 않습니다. `--name=<name>`은 자기 인스턴스를 만듭니다. 서비스는 `<name>`과 `<name>-admin`이고, Linux 사용자, 디렉터리, WinSW id가 이름을 따르므로 인스턴스 둘(또는 아직 1.x가 도는 호스트 옆의 인스턴스)을 각자의 포트로 한 호스트에 둘 수 있으며, Java가 무엇이든 만들기 전에 이름을 검증합니다. 두 서버는 어떤 사람에게도 속하지 않는 서비스 계정 하나(Linux는 `pg-ledger-mcp`, Windows는 LocalService)로 실행하며, 비밀 디렉터리는 그 계정만 읽을 수 있습니다(Windows에서는 설치한 사용자와, 읽기만 하는 LocalService).
- 데이터베이스 계정 둘: 앱 계정에는 `migrate --app-account=<account>`가 `dml-grants.sql`의 최소 권한(ANSI `GRANT`만, DDL 없음, 이력에 `UPDATE`와 `DELETE` 없음)을 부여하고, DDL 계정은 `migrate --owner-account=<account>`에 쓰며 그 비밀번호는 숨김 입력으로 받고 저장하지 않습니다.
- 설치의 설정은 한 디렉터리(`ledger.secrets.home`)에 있습니다. 설치기가 렌더하는 `application.yaml`과 서비스별 파일 하나씩, 그리고 운영자의 설정을 위한 `local.yaml`(교체하지 않습니다)입니다.
- `token-generate`는 bearer 토큰과 관리 토큰을 `SecureRandom`의 32바이트로 만들고, 다시 실행해도 이미 있는 토큰은 유지합니다.
- 스키마 파일 `V{n}__*.sql`과 이력 표 `schema_history`를 `migrate`가 적용하며, 바뀐 파일이 있으면 `migrate`는 아무것도 적용하기 전에 멈추고 모든 프로세스도 시작할 때 멈춥니다. 이력 표는 버전의 시도마다 한 행을 가집니다(`version`, `attempt`, `script`, `digest`, `applied_at`, `outcome`은 `SUCCEEDED` 또는 `FAILED`이며 세 제품이 같은 형입니다). 시도 하나는 트랜잭션 하나이고, `migrate`를 동시에 두 번 실행해도 안전합니다(두 번째는 데이터베이스에서 기다린 뒤 첫 번째가 적용한 것을 건너뜁니다). 스키마 파일의 긴 텍스트 타입은 `SqlBuilder`의 방언이 선언하며 `migrate`가 연결의 제품 이름에서 방언을 가져오므로 그에 대한 설정과 설치기 옵션은 없고, 데이터베이스 인코딩은 UTF-8이어야 합니다. `migrate`는 아무것도 바꾸기 전에 같은 방언이 제품마다 적는 탐침 질의로 세 글자(한글 두 자와 이모지 하나)의 텍스트를 보내, 데이터베이스가 다른 길이나 다른 텍스트를 돌려주면 진행을 거부하며(`SCHEMA_ENCODING_NOT_UTF8`), 데이터베이스의 문자 집합 목록은 읽지 않고 문자 집합 이름도 비교하지 않습니다. 장부는 Flyway를 쓰지 않으며(DBMS마다 모듈이 필요합니다) 서버가 DDL 비밀번호를 갖지 않으므로 `ledger-cli migrate`로 마이그레이션합니다.
- 장부 데이터베이스의 첫 설정 `setup`: `migrate`처럼 마이그레이션하고, 앱 계정이 스키마를 쓸 수 있는지 확인하며(쓸 수 없으면 종료 코드 `3`과 빠진 단계를 알림), 없는 시드 코드를 `code-set`이 쓰는 서비스로 추가하고, 시드와 데이터베이스를 개수와 SHA-256 다이제스트로 대조합니다. 다시 실행해도 아무것도 바뀌지 않습니다. 설치기가 호출합니다.
- `ledger-cli.jar` 안의 시드 번들 `ledger-seed.mv.db`: 빌드가 `src/seed/issue-categories.tsv`와 `src/seed/install-defaults.properties`에서 만들며(모듈 `ledger-seed`), 기본 결함 분류 14개와 설치 기본값이 들어 있습니다. H2 데이터일 뿐이며, 장부는 언제나 운영자가 설치한 데이터베이스 시스템에 저장되고 H2 드라이버나 H2의 JDBC URL의 등록은 거절됩니다. H2 드라이버는 `ledger-cli`만 가지며, MCP 서버와 관리 웹에는 없습니다.
- `install-default <name>`: 설치 기본값(`instance-name`, `mcp-port`, `admin-port`)은 시드 번들에 한 번만 적고, `render-deploy`, `prepare-host`, `mcp-check`와 두 설치기가 거기서 가져옵니다.
- 개인판: 한 사람이 본인의 컴퓨터나 본인의 서버에 설치하며 설치 대상 전체를 신뢰합니다. MCP 서버와 관리 웹은 `127.0.0.1`에서만 수신하며, 이는 두 서버의 코드에 고정되어 있습니다(주소를 바꾸는 설정은 없고 `server.address`는 효과가 없습니다). 액추에이터는 서버와 같은 포트(`/healthz`)를 쓰며, `management.server.port`가 `server.port`와 다른 서비스는 시작하지 않습니다(`MANAGEMENT_PORT_SEPARATE`). 그 두 번째 수신 포트는 루프백에 묶이지 않기 때문입니다. 다른 컴퓨터에서 접근하게 하는 일, 곧 역방향 프록시와 TLS 인증서는 운영자가 고른 도구로 하는 운영자의 몫이며, 설치기는 프록시 설정을 쓰지 않고, 인증서를 발급하지 않고, 갱신 타이머를 설치하지 않습니다.
- `--mcp-host`와 `--admin-host`는 각각 호스트 이름 하나(운영자의 역방향 프록시가 `Host` 헤더로 넘기는 이름)를 받으며 둘 중 하나만 줄 수 있습니다. 서비스의 `Host` 검사는 그 이름을 `127.0.0.1`과 `localhost`(항상 허용)에 더해 허용하며, `--admin-host`가 있으면 설치기가 그 이름의 passkey 설정도 씁니다.
- 배포 설정: `ledger.admin.agent-token`은 필수이며 `ledger.admin.token`과 달라야 하고, `ledger.admin.lockout.global-delay`는 기간 안에 한도보다 많은 자격 증명 확인이 들어올 때 확인을 늦춥니다(잠그거나 거절하지 않습니다. 결함 D-0013: 클라이언트 주소별 잠금은 운영자의 프록시 뒤에서 소유자를 잠갔으므로 `ledger.admin.lockout.max-failures`와 `ledger.admin.lockout.lock-period` 설정은 없습니다).

### 변경

- PostgreSQL 함수와 트리거가 강제하던 규칙(부여, 상태 전이, 같은 세션 거절, 영수증, ID 부여, 생성 출처)은 같은 오류 토큰으로 응용 서비스가 강제합니다.
- 애플리케이션에는 이력을 수정하거나 삭제하는 경로가 없으며, 데이터베이스 모듈의 부여 템플릿(`dml-grants.sql`)은 애플리케이션 계정에 이력의 `UPDATE`와 `DELETE`를 주지 않습니다.
- 시각은 모든 곳에서 UTC이며, 관리 웹은 브라우저의 지역 시각으로 표시합니다.
- 2.0.0부터 라이선스를 MIT License에서 GNU Affero General Public License v3.0 또는 (선택에 따라) 그 이후 판(`AGPL-3.0-or-later`)으로 바꿉니다. `LICENSE`에는 수정하지 않은 GNU AGPL v3 원문을 두며, 이후 판의 선택은 README에 밝힙니다. `AGPL-3.0-or-later`는 2.0.0과 그 이후에 공개하는 모든 릴리스에 적용하며, 이후에 공개하는 1.x 계열의 유지보수 릴리스도 포함합니다. MIT License는 이미 그 라이선스로 공개한 사본, 곧 v1.0.0과 v1.1.0에만 계속 적용합니다. 제13조에 따라, 수정한 버전을 네트워크 서비스로 운영하는 자는 그 이용자에게 해당 소스 코드를 제공해야 합니다. 관리 웹은 각 페이지 하단에 소스 코드 링크를 보여 주며, 그 주소는 설정 `ledger.source.url`(기본값은 프로젝트의 공개 저장소)입니다. 수정한 버전을 운영하는 자는 이 설정을 그 버전의 소스를 제공하는 곳으로 지정합니다.
- MCP 서버와 관리 웹은 서비스 계정 하나로 실행하며 root로는 실행하지 않습니다.
- 설치기는 이전에 `migrate`를 부르던 자리에서 `setup`을 부릅니다. 같은 옵션이면 `render-deploy`가 쓰는 파일은 바이트 단위로 같으며, 바뀐 것은 기본값을 두는 곳뿐입니다.
- 시드와 데이터베이스를 대조하는 `setup`의 줄은 시드와 다른 코드가 무엇인지 말합니다. 그 코드는 시드와 다르지만 그대로 둔 것이며, 운영자가 바꿨거나 `import-1x`가 1.x에서 가져온 것입니다. 개수와 종료 코드는 바뀌지 않았습니다.
- MCP 서버는 시작할 때 `Replace existing Tool` WARN을 남기지 않습니다. Spring AI의 어노테이션 스캐너를 끄므로(`spring.ai.mcp.server.annotation-scanner.enabled`) 도구는 카탈로그만 자기 정의로 등록합니다. 도구의 이름, 키, 결과는 바뀌지 않았고 SDK 로거의 수준도 낮추지 않았습니다.
- 두 이슈 사이의 관계는 종류에 방향이 있으면 그 방향을 유지합니다. 1.x는 모든 관계를 작은 ID가 앞에 오도록 저장했으므로 `caused_by`(a의 원인은 b)와 `blocks`(a가 b를 차단)는 어느 이슈가 주어인지 잃었습니다. 이제 방향은 관계 종류 코드의 속성입니다(`common_code.direction`: `GIVEN`은 `a`, `b`를 호출자가 준 순서대로 유지하고, `CANONICAL`은 정렬된 순서를 유지하므로 (a, b)와 (b, a)는 하나의 관계입니다). `caused_by`와 `blocks`는 `GIVEN`이며, `code-set --direction=<direction>`이나 관리 콘솔로 추가하는 종류는 자기 방향을 정합니다. `ledger_issue`는 그 이슈가 어느 끝(`a` 또는 `b`)인지 알려 주고, `ledger_codes`는 방향을 알려 주며, `ledger_link` 정의는 방향이 있는 종류를 표시합니다. 관계 표 `issue_relation`의 `CHECK (a < b)`는 `CHECK (a <> b)`입니다(스키마 파일 `V4__relation_direction.sql`).
- `import-1x`는 1.x의 `caused_by`, `blocks` 관계의 방향을 복원할 수 없습니다. 1.x는 호출자가 어느 이슈를 먼저 적었는지 어디에도 남기지 않았기 때문입니다. 그래서 저장된 그대로 가져오고(짐작하지 않습니다) 건수와 ID를 나열하며, 감사 행과 `--verify-only`에도 나옵니다. 확인하여 방향이 거꾸로인 관계는 제거한 뒤 `ledger_link`로 다시 연결합니다.
- 설치기가 렌더하지 않은 파일을 렌더한 파일이 대체하면 그 파일은 `<file>.backup`으로 보관합니다.
- 다른 장부에서 온 이력 항목은 중립적인 이름 `IMPORTED_*`(연산 `IMPORT`, `IMPORTED_NOTE`, `IMPORTED_CHANGE`, 보증 수준 `IMPORTED_LOGIN`, `IMPORTED_SHARED`, `IMPORTED_UNKNOWN`)과 읽기 도구의 필드 `source_ref`를 씁니다. `import-1x`가 1.x의 값을 이 이름으로 바꿉니다. 쓰기 도구에는 `author_id` 인자가 없으며, 작성자는 검증된 호출자입니다.
- 쓰기 도구의 규칙 네 가지가 더 엄격해졌습니다. `VERIFIED` 개체에는 `ledger_record_deliverable`도 수정도 허용되지 않으며(`VERIFIED_ENTITY`), 검토자가 먼저 `ledger_review`로 다시 열어야 합니다. 이슈는 그것을 등록하지 않았고 사례를 기록하지 않았고 산출물을 기록하거나 수정하지 않은 세션만 검수할 수 있고, 명세나 작업은 그것을 만들지 않았고 소유하지 않으며 산출물 기록이나 완료 보고를 한 적이 없는 세션만 검수할 수 있고, 마일스톤 기준은 그것을 등록하거나 완료하지 않은 세션만 `MET`이나 `NOT_MET`으로 정할 수 있습니다(`SAME_SESSION`. 병합된 이슈의 사례와 등록 세션도 그 이슈의 것으로 칩니다). 호출자가 정하는 이슈 ID와 `<CODE>-S-0001` 또는 `<CODE>-T-0001` 형식의 ID는 번호가 프로젝트의 다음 번호를 넘지 않아야 하며, 넘는 번호는 `ID_NUMBER_AHEAD`로 거절되고, 그동안 다른 요청이 그 번호를 가져갔으면 `ID_COUNTER_CHANGED`가 요청을 다시 보내라고 알립니다. 이런 ID는 서버가 적는 형식으로만 저장하며, `<CODE>-D-00002`와 번호 0은 경로 `id`의 `VALIDATION_FAILED`로 거절합니다. `ledger_link`와 다른 프로젝트의 이슈로의 병합은 두 프로젝트 모두에서 해당하는 부여를 요구합니다.
- 명령줄 도구는 옵션 없이도 그 호스트의 설치 프로그램이 설치를 둔 곳에서 설치를 찾습니다. `ledger.secrets.home`의 기본값은 Linux에서 `/etc/<name>`, Windows에서 `C:/ProgramData/<name>/etc`입니다(결함 D-0089). 모든 프로그램(명령줄 도구, MCP 서버, 관리 웹, 이전 도구)은 시작할 때 자기 JVM의 시간대를 UTC로 설정하므로, 호스트의 시간대가 UTC가 아니어도 명령에 `-Duser.timezone=UTC`가 필요 없습니다(결함 D-0090). 파일 시스템의 종류(POSIX 권한, ACL, DOS 속성)에 따라 달라지는 일은 한 모듈 `ledger-files`에서 정합니다(결함 D-0091, D-0092). `stop-1x`의 Linux 호출은 `DeployLayout`의 경로를 쓰는 클래스 하나, `SystemdServices`에 있습니다(결함 D-0093). 실패한 `prepare-host`는 Windows에서 ACL을 되돌리던 것처럼 Linux에서도 디렉터리의 권한과 소유자를 되돌립니다(결함 D-0094). 훅의 키 저장소는 서버와 명령줄 도구처럼 프로세스의 계정(`user.name`이 아니라 Windows에서 `DOMAIN\name`)을 가리키고, 첨부 폴더에서 같은 이름의 파일 위로 파일을 옮기지 않으며, `install.cmd`는 서비스 상태를 기계 언어로 된 단어가 아니라 `sc.exe query`의 숫자로 읽고, README는 Windows PowerShell 5.1이 `--stdin`으로 파이프한 비밀을 어떻게 인코딩하는지 설명합니다(결함 D-0095).
- 분류나 심각도를 저장하는 쓰기(`ledger_issue_save`)만 해당 공통코드를 검사합니다. 상태 전이는 검사하지 않으므로 폐기된 심각도 `UNRATED`를 아직 가진 가져온 이슈도 진행, 검수, 병합을 할 수 있고 등급은 수정으로 매깁니다.

- DBHub, Node, Node 훅 스크립트. Java 서버, Java 관리 웹, 훅 jar가 대체합니다.
- 1.x의 PostgreSQL 함수, 트리거, 로그인 역할. 작성자와 검토자 로그인은 이제 도구의 채널입니다.
- 도구 `execute_sql_reader`와 `search_objects_reader`.
- 비밀이 든 환경 파일. `deploy/`의 1.x 셸 설치 스크립트, 유닛 템플릿, 도메인 자동화는 설치기 두 개로 대체되어 제거되었으며, 저장소의 이력에 남아 있습니다.
- 2.0 개발 중 저장소에 남겨 둔 1.x 구현(`bin/`, `web/`, `mcp/`, `sql/`, `tests/`). 1.x 소스는 태그 `v1.1.0`에서 볼 수 있습니다.
- 2.0의 서비스, 설치기, `ledger-cli`에 있던 1.x 처리 전부: 1.x의 타입, SQL, 설정, 환경 파일이 더 이상 남아 있지 않습니다. 설치기, `render-deploy`, `prepare-host`의 옵션 `--from-1x-env=<file>`은 없어졌고, `ledger-cli` 명령 `secret-import-1x`, `import-legacy`, `retire-legacy`도 없어졌습니다. `ledger-migrate-1x.jar`의 명령 `import-secrets-1x`, `import-1x`, `retire-1x`가 이를 대체하고, `stop-1x`는 1.x 서비스를 직접 멈추는 일을 대체합니다.
- 충돌 코드 `REQUEST_ID_LEGACY`와 1.x에서 가져온 영수증. `import-1x`는 요청 영수증을 복사하지 않습니다.

### 보안

- 결함 D-0012를 수정했습니다. 1.x는 `_hostAttestation`을 검증하지 않아 bearer 토큰을 가진 쪽이 다른 세션의 이름으로 쓸 수 있었습니다. 이제 서버는 소유자가 작성자와 서버에 대해 등록한 키로 만든 Ed25519 서명을 검증하고, 도구, 작업 키, 인자, 시각(`ledger.attestation.window`)을 확인합니다.
- 한 서버용 서명은 다른 서버에서 검증되지 않으며, 키가 없는 경우와 서명이 틀린 경우는 구별되지 않습니다.
- 관리 웹은 에이전트의 토큰을 거절하고(`AGENT_TOKEN_FORBIDDEN`), 많은 자격 증명 확인을 늦추되 맞는 자격 증명을 잠그거나 거절하지 않으며(`ledger.admin.lockout.*`, 결함 D-0013), CSRF 토큰과 `Secure`, `SameSite=Strict` 세션 쿠키를 사용합니다.
- 비밀은 숨김 입력으로 비밀 저장소에서 읽으며 출력하지 않습니다(토큰은 만들 때 `token-generate --print`가 한 번만 보여 줍니다). 비밀 디렉터리는 소유자 전용(POSIX 권한, Windows에서는 ACL)이며 서비스 계정만 읽을 수 있고(Windows에서는 설치한 사용자와, 읽기만 하는 LocalService), 그래서 장부의 비밀을 사람의 계정과 에이전트로부터 떼어 놓습니다. 비밀은 용도마다 폴더 하나(`common`, `admin`, `mcp`, `tool`)에 두며, 각 서비스와 도구는 자기에게 필요한 폴더만 각각 별도의 설정 트리로 읽어 들입니다(결함 D-0031). 그래서 MCP 서버의 `Environment`에는 관리 토큰이나 OpenID Connect 클라이언트 비밀이 더 이상 들어오지 않습니다. 첨부의 키 파일은 어떤 설정 트리 아래에도 없는 `<settings folder>/attachment-keys`에 둡니다(Spring Boot는 트리 아래의 모든 파일을 그 프로세스의 속성으로 만듭니다). 두 서비스는 같은 운영체제 사용자로 실행되므로 파일 권한이 한 서비스가 다른 서비스의 폴더를 읽는 것을 막지는 못합니다.
- DDL 계정의 데이터베이스 비밀번호는 한 번의 실행을 위해 입력받으며 저장하지 않습니다. 앱 계정에는 DDL 권한이 없고 이력의 `UPDATE`와 `DELETE`도 없습니다.

### 요구 사항

- MCP 서버와 관리 웹의 호스트(서비스 계정도 실행하므로 모든 계정이 실행할 수 있는 경로, 즉 `/home` 아래가 아닌 곳이어야 하며, `deploy/install.sh`는 `--java=<path>`를 받아 이를 확인합니다), 그리고 훅 jar를 쓰는 모든 클라이언트 호스트에 Java 25 런타임이 필요합니다(클래스 파일 버전 69.0이며, 더 낮은 JVM은 `UnsupportedClassVersionError`로 거부합니다). 빌드에는 JDK 25가 필요합니다.
- 밖에서 접근하려면 같은 호스트에 운영자가 고른 역방향 프록시와 TLS 인증서가 있어야 하며, 프록시는 `Host` 헤더를 그대로 넘깁니다(프록시는 긴 MCP 연결을 유지해야 합니다). 설치기는 이를 제공하지 않습니다.
- 사용자가 직접 구해 `driver-register`로 등록하는 JDBC 드라이버. 제품은 드라이버를 동봉하지 않습니다. 세션 시간대가 UTC이고, UTF-8을 사용하며, 문자열을 대소문자를 구분하여 비교하는 데이터베이스. 시험하는 데이터베이스는 PostgreSQL이며 다른 제품은 시험하지 않았습니다.
- systemd가 있는 Linux, 또는 JDBC 드라이버처럼 직접 구하는 WinSW 2.x 실행 파일이 있는 Windows. 설치기는 아무것도 동봉하거나 내려받지 않습니다.
- 1.x 설치를 옮기려면: jar `ledger-migrate-1x.jar`(다른 jar와 함께 빌드하며 Java 25 런타임이 필요합니다)와, `stop-1x`를 위한 root와 `systemctl`(1.x 호스트는 Linux 호스트입니다)이 필요합니다. 1.x 장부는 마지막 설치 단계(관찰된 사례, 공통코드, 생성 출처)까지 완료되어 있어야 하며, 그렇지 않으면 `import-1x`가 거부합니다. `import-1x`가 읽는 1.x 장부는 PostgreSQL 데이터베이스입니다.
- 클라이언트 호스트와 서버의 시계가 `ledger.attestation.window`(기본 5분) 안에서 맞아야 합니다.

### 알려진 제한

- macOS는 지원하지 않습니다.
- 파일 보호와 설치 프로그램은 Windows 기본 제공 계정(`NT AUTHORITY\LocalService`, `NT AUTHORITY\SYSTEM`, `BUILTIN\Administrators`)을 영어 이름으로 가리킵니다. JDK가 SID로 계정을 찾을 수 없기 때문이며, 이름이 다른 언어의 Windows에서는 시험하지 않았습니다. `--java`와 `--home`은 평범한 경로 구간만 받으므로(Windows의 `--java`는 공백도 받습니다) 괄호가 든 경로(`Program Files (x86)`)나 ASCII 밖 글자가 든 경로는 거절하며, `install.cmd`는 `PATH`의 `java`를 씁니다.
- 모델 문맥 밖에서 PC의 파일을 직접 전송할 때는 `artifact_begin` 뒤와 `artifact_finish` 앞에 `ledger-cli attachments-prepare`와 `ledger-cli attachments-send`를 사용합니다.
- 행을 식별하는 텍스트(조건의 release나 code, 수정 기록의 저장소, 제목)가 1.x 장부에서 비어 있으면 NULL로 저장하지 않습니다. `import-1x`가 그 행을 나열하고 아무것도 쓰지 않으므로 1.x 장부에서 고쳐야 합니다. 긴 텍스트 다섯 열의 빈 문자열은 가져옵니다(위 참조).
- `driver-register`는 장부 데이터베이스의 스키마가 아직 마이그레이션되지 않았을 때도(첫 설치, 또는 스키마를 지운 뒤의 재실행) 등록 파일을 쓰며, 소유자 감사 기록의 행은 아직 남지 않았다고 알립니다. 스키마가 준비되면 `migrate`와 `setup`이 그 행을 한 번 기록합니다.
- Windows에서는 설치기를 같은 사용자로 다시 실행합니다. 비밀은 설치한 사용자의 것(LocalService는 읽기만)입니다.
- 스키마를 쓸 수 있는 권한은 데이터베이스 시스템의 문장이며 제품 SQL에 포함되지 않습니다. 앱 계정에 그 권한이 없으면 `setup`이 확인하고 종료 코드 `3`으로 멈춥니다. 운영자가 권한을 주면 `setup`이 멈춘 곳에서 이어집니다. `setup`은 이미 있는 코드를 바꾸지 않으므로, 이후 버전이 시드 코드를 바꿔도 기존 장부의 코드는 바뀌지 않습니다. 그럴 때는 `code-set`을 씁니다.
- `deploy\install.cmd`는 `install.sh`처럼 `--stdin`을 (첫 번째 인자로) 받아 비밀번호를 표준 입력에서 읽으므로, Windows 설치에 터미널 앞의 사람이 필요하지 않습니다. 운영체제 사용자 생성, 그 사용자로 전환, 서비스 관리자는 Java에 해당 API가 없어 스크립트에 남습니다. 폴더 변경에는 root(Windows에서는 관리자 권한 프롬프트)가 필요하며 사전 점검은 없고, Java가 `HOST_FAILED`로 거부합니다.
- Windows에서는 비밀을 서비스 계정에 넘기지 않습니다. 설치한 사용자가 소유하고 LocalService가 읽으므로 `ledger-cli`의 소유자 명령은 설치한 사용자에게 계속 동작합니다(관리 웹은 소유자 작업을 하는 다른 자리입니다).
- 같은 운영체제 사용자의 다른 프로세스는 세션 키 파일을 읽을 수 있으므로, 한 사용자 안의 격리에는 별도 계정이 필요합니다.
- 개인판은 PC 전체를 신뢰합니다. 훅과 명령줄 도구는 기존 키 폴더, 키 파일, 비밀을 누가 접근할 수 있든, 누가 소유하든, 링크를 거쳐 있든 그대로 읽고, 새로 만드는 것은 소유자 전용으로 만듭니다. 종류가 맞지 않는 경로(파일 자리의 디렉터리)와 빈 파일만 거절합니다.
- 시간 창 안에서 다시 보낸 서명 토큰은 같은 호출을 반복할 수만 있고 다른 내용을 실을 수 없습니다. 이 창은 일회용 토큰이 아닙니다.
- MCP 서버, 관리 웹, 소유자 명령은 앱 계정 하나를 함께 쓰므로(서비스 계정은 비밀을 떼어 놓을 뿐 데이터베이스의 권한을 나누지 않습니다), 침해된 MCP 서버 프로세스는 세션 키와 부여도 쓸 수 있는 권한을 가집니다.
